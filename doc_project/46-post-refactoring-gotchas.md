# 🪲 Грабли после рефакторинга Visary.Api.Client

## 📋 Описание

После выделения `Visary.Api.Client` в отдельный проект (см. `39-visary-api-refactoring.md`, `40-visary-api-refactoring-completed.md`) три связанные сборки/конфигурации остались несогласованными с новой структурой и **молча ломали запуск** при деплое в Docker. Этот документ фиксирует все три проблемы, чтобы при следующем рефакторинге не повторить.

> 🔁 См. также: `13-vite-proxy-backend.md`, `19-net10-deployment-gotchas.md`, `40-visary-api-refactoring-completed.md`, `26-troubleshooting.md`.

## 🐛 Проблема 1. Dockerfile не видит соседний проект

### Симптом

```
docker compose build backend
...
Skipping project "/Visary.Api.Client/Visary.Api.Client.csproj" because it was not found.
...
error CS0246: The type or namespace name 'IListViewClient' could not be found
error CS0246: The type or namespace name 'ICrudClient' could not be found
error CS0400: The type or namespace name 'Visary' could not be found in the global namespace
```

В рантайме (если кто-то закоммитил старый образ): `404 Not Found` на `POST /api/sites/sync/{id}`, потому что **`SitesController` отсутствует в `KiloImportService.Api.dll`** — фактически образ собран на старом коде до рефакторинга.

Быстрая диагностика:

```powershell
docker exec kilo-import-backend sh -c "strings /app/KiloImportService.Api.dll | grep -i 'Controller$'"
# Видим список — если SitesController отсутствует, образ устарел.
```

### ❌ Что было неправильно

`docker-compose.yml`:
```yaml
backend:
  build:
    context: ./KiloImportService.Api      # 👈 ограничивает доступные файлы только этой папкой
    dockerfile: Dockerfile
```

`KiloImportService.Api/Dockerfile`:
```dockerfile
COPY KiloImportService.Api.csproj .
RUN dotnet restore                        # 👈 не видит ../Visary.Api.Client
COPY . .
RUN dotnet publish ...
```

Контекст билда — папка `KiloImportService.Api`. Соседний `Visary.Api.Client` (в родительской папке) Docker-у недоступен в принципе.

### ✅ Правильная реализация

Поднять контекст билда на корень репо и явно копировать оба проекта:

`docker-compose.yml`:
```yaml
backend:
  build:
    context: .                                       # 👈 корень репо
    dockerfile: KiloImportService.Api/Dockerfile
```

`KiloImportService.Api/Dockerfile`:
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0-preview-alpine AS build
WORKDIR /src

# Сначала только .csproj обоих проектов — для кэша restore
COPY KiloImportService.Api/KiloImportService.Api.csproj KiloImportService.Api/
COPY Visary.Api.Client/Visary.Api.Client.csproj         Visary.Api.Client/
RUN dotnet restore KiloImportService.Api/KiloImportService.Api.csproj

# Потом исходники обоих проектов
COPY KiloImportService.Api/  KiloImportService.Api/
COPY Visary.Api.Client/      Visary.Api.Client/
RUN dotnet publish KiloImportService.Api/KiloImportService.Api.csproj -c Release -o /app /p:UseAppHost=false
```

И **обязательно** `.dockerignore` в корне, иначе `COPY` затащит фронтенд / тесты / `bin/obj` — раздует контекст до сотен МБ:

```gitignore
**/bin/
**/obj/
KiloImportService.Web/
KiloImportService.Api.Tests/
db/
doc_project/
*.md
.git/
```

### ⚠️ Важно

- При добавлении нового **отдельного** проекта (например, `KiloImportService.Domain`) — добавлять явный `COPY <project>/<project>.csproj <project>/` **перед** `dotnet restore`, иначе кэш restore сломается на CI.
- Не использовать `COPY . .` без `.dockerignore` — попадут `node_modules` фронтенда и логи Postgres.
- Файл `.dockerignore` ищется **в корне build context**, а не рядом с Dockerfile.

## 🐛 Проблема 2. EF mapping не совпадает со схемой БД-снимка

### Симптом

```
POST /api/sites/sync/7847 → 500
{"error":"internal_error","message":"42703: column c.FinishingMaterialId does not exist\n\nPOSITION: 121"}
```

В Visary CRUD данные есть, токен валиден, но локальный upsert в `visary_webapi_db` падает.

### Причина

`SitesSyncService.UpsertAsync` пишет `entity.FinishingMaterialId = raw.FinishingMaterialId`, а в `VisaryDbContext` есть mapping:

```csharp
e.Property(x => x.FinishingMaterialId).HasColumnName("FinishingMaterialId");
```

Но init-скрипт `db/visary/init/02-missing-roots.sql` создаёт таблицу `Data."ConstructionSite"` **без этой колонки** — её там просто 11 штук. Колонка появилась в C#-сущности при работе над фичей "Финмодель" (см. `22-update-finishing-material.md`, `23-finmodel-import.md`), но в SQL-схеме её забыли.

Это «снимок Visary» — БД управляется не EF-миграциями, а руками через init-скрипты в `db/visary/init/`. Поэтому EF миграции тут не помогут — нужно править SQL.

### ✅ Правильная реализация

1. **Добавить колонку в init-скрипт** для будущих чистых deploy:

`db/visary/init/02-missing-roots.sql`:
```sql
CREATE TABLE IF NOT EXISTS "Data"."ConstructionSite" (
    "ID"                            integer GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    ...
    "Hidden"                        boolean NOT NULL DEFAULT false,
    "Version"                       timestamp with time zone,
    "FinishingMaterialId"           integer,    -- 👈 добавлено
    CONSTRAINT "PK_ConstructionSite" PRIMARY KEY ("ID")
);
```

2. **Не пересоздавая БД** (`docker compose down -v` снёс бы все импорты), накатить ALTER через идемпотентный `IF NOT EXISTS`:

```powershell
'ALTER TABLE "Data"."ConstructionSite" ADD COLUMN IF NOT EXISTS "FinishingMaterialId" integer;' `
  | docker exec -i kilo-import-pg-visary psql -U visary -d visary_webapi_db
```

### ⚠️ Важно

- Visary-БД управляется init-скриптами `db/visary/init/*.sql`, **не EF-миграциями**. Они выполняются Postgres-контейнером **только при первом старте volume**. Чтобы пересоздать БД с новым init — `docker compose down -v` (потеряете данные).
- На каждое изменение C#-сущности `Visary.Api.Data.Visary.Entities.*` обязательно проверять, что соответствующая колонка существует в `02-missing-roots.sql` (для корневых таблиц `ConstructionProject` / `ConstructionSite`) или в `01-schema.sql` (для остальных).
- Для уже работающих локальных БД использовать `ADD COLUMN IF NOT EXISTS` через `psql` — это идемпотентно и безопасно.
- Тип колонки в SQL должен совпадать с C# по nullability: `int?` → `integer NULL`, `int` → `integer NOT NULL`.

## 🐛 Проблема 3. AddHttpClient после удаления HttpClient из конструктора

### Симптом

```
GET /api/projects/search?q=доу&limit=50 → 500
System.InvalidOperationException: A suitable constructor for type 'ProjectsCacheService' could not be located.
A Typed client must provide a constructor taking a 'System.Net.Http.HttpClient' as a parameter.
```

### Причина

До рефакторинга `ProjectsCacheService` ходил в Visary через сырой `HttpClient` и регистрировался как **Typed HttpClient**:

```csharp
// Program.cs (до рефакторинга)
builder.Services.AddHttpClient<IProjectsCacheService, ProjectsCacheService>(...)
    .ConfigurePrimaryHttpMessageHandler(...);
```

Это требует **обязательного** `HttpClient`-параметра в конструкторе сервиса (документировано в [DefaultTypedHttpClientFactory](https://learn.microsoft.com/en-us/dotnet/core/extensions/httpclient-factory)).

После рефакторинга `ProjectsCacheService` стал зависеть от **`IListViewClient`** из `Visary.Api.Client` (который уже зарегистрирован через `AddVisaryClient(...)` ранее в `Program.cs`):

```csharp
public ProjectsCacheService(
    ImportServiceDbContext db,
    IListViewClient visaryClient,            // 👈 теперь IListViewClient, не HttpClient
    IOptions<VisaryOptions> options,
    ILogger<ProjectsCacheService> log)
```

Регистрацию в `Program.cs` забыли поправить — она по-прежнему пыталась активировать сервис как Typed HttpClient → DI не нашёл подходящий конструктор → 500 на любой запрос к `/api/projects/...`.

### ✅ Правильная реализация

`Program.cs`:
```csharp
// ─── Visary HTTP API клиент + кэш проектов ───
builder.Services
    .AddVisaryClient(opt =>
    {
        opt.BaseUrl = builder.Configuration["Visary:BaseUrl"] ?? string.Empty;
        opt.BearerToken = builder.Configuration["Visary:BearerToken"] ?? string.Empty;
        opt.RequestTimeout = TimeSpan.FromSeconds(30);
    })
    .Configure<VisaryOptions>(builder.Configuration.GetSection(VisaryOptions.SectionName));

// ProjectsCacheService теперь использует IListViewClient (см. AddVisaryClient выше),
// а не сырой HttpClient. Регистрируем как обычный scoped-сервис.
builder.Services.AddScoped<IProjectsCacheService, ProjectsCacheService>();
builder.Services.AddScoped<ISitesSyncService, SitesSyncService>();
```

### ❌ Что НЕ делать

```csharp
// ❌ AddHttpClient требует HttpClient в конструкторе сервиса.
// Если конструктор принимает абстракцию (IListViewClient/ICrudClient) — будет 500.
builder.Services.AddHttpClient<IProjectsCacheService, ProjectsCacheService>(...);
```

### ⚠️ Важно

- `AddHttpClient<TService, TImpl>(...)` имеет смысл **только** когда `TImpl` — это сам HTTP-клиент (т.е. напрямую инкапсулирует `HttpClient`). Для бизнес-сервисов, которые **используют** клиент через интерфейс — обычный `AddScoped`/`AddTransient`.
- Все настройки `HttpClient` (timeout, SSL, retry) после рефакторинга живут внутри `Visary.Api.Client.AddVisaryClient`. Дублировать их через `ConfigurePrimaryHttpMessageHandler` в `Program.cs` не нужно.
- При переезде сервиса с сырого `HttpClient` на типизированный клиент-абстракцию — **всегда** проверять регистрацию в `Program.cs` и удалять остатки `AddHttpClient<>`.

## 🎯 Общий чек-лист после рефакторинга, выделяющего проект-библиотеку

При вынесении кода в новый `*.csproj`-проект (как `Visary.Api.Client`) перед PR-ом проверить:

- [ ] **Docker build context** покрывает оба проекта (контекст = корень репо или общая родительская папка)
- [ ] **Dockerfile** копирует `.csproj` нового проекта **до** `dotnet restore` (для кэша слоёв)
- [ ] **Dockerfile** копирует исходники нового проекта **до** `dotnet publish`
- [ ] **`.dockerignore`** в корне исключает фронтенд/тесты/`bin`/`obj`/`node_modules`
- [ ] Локальная сборка на хосте (`dotnet build`) **не показывает**, что Docker сломан — обязательно прогнать `docker compose build backend` локально
- [ ] **Все DI-регистрации** сервисов, у которых поменялся конструктор, обновлены (`AddHttpClient<>` → `AddScoped<>`, и т.п.)
- [ ] **Schema БД** (init-скрипты) актуальна для всех новых полей в C#-сущностях, маппящихся в БД
- [ ] **Smoke-тест** пройден после `docker compose up -d --build`: GET `/health`, GET `/api/projects/search`, POST `/api/sites/sync/{id}`
- [ ] **Frontend** в Docker (или `npm run dev`) пингует backend без 404/500
- [ ] **Логи backend** при первом запросе чистые — нет `Skipping project`, `column does not exist`, `suitable constructor`

## 🧪 Smoke-тест

```powershell
# 1. Сборка и запуск
docker compose build backend
docker compose up -d backend

# 2. Health-check
Invoke-WebRequest http://localhost:5000/health -UseBasicParsing

# 3. Проверка контроллеров в собранном образе
docker exec kilo-import-backend sh -c "strings /app/KiloImportService.Api.dll | grep -i 'Controller$'"
# Ожидается: Health, ImportTypes, Sites, Projects, Imports

# 4. Поиск проектов (проверяет ProjectsCacheService → IListViewClient)
Invoke-WebRequest "http://localhost:5000/api/projects/search?q=test&limit=5" -UseBasicParsing

# 5. Sync объекта (проверяет SitesSyncService + EF mapping + БД-схему)
Invoke-WebRequest "http://localhost:5000/api/sites/sync/<existing_site_id>" -Method POST -UseBasicParsing
```

Все четыре запроса должны вернуть `200 OK`. Если хоть один из них даёт `404 / 500` — см. соответствующий раздел выше.
