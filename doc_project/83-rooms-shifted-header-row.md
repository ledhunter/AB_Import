# 🪞 Импорт «Помещения»: смещённая строка заголовков (`HeaderAnchors`)

## 📋 Описание

**Статус**: ✅ Реализовано
**Дата**: 2026-05-18
**Дополняет**: [68-rooms-import.md](68-rooms-import.md)

Пользовательские файлы реестра квартир далеко не всегда повторяют структуру
эталона «Пример импорта.xlsx», где **строка 1 = шапка**. В реальном файле
`Ежевика короткая 1.xlsx` (полученном от заказчика 2026-05-18) первые строки
выглядят так:

| Строка | Что в ней                                                              |
|-------:|------------------------------------------------------------------------|
| 1      | «Реестр вывода КВАРТИР» (объединённая ячейка, заголовок документа)     |
| 2      | «Стоимость кв.м/ руб.» — подсказка                                      |
| 3      | «Дисконт» / коэф. Кб                                                   |
| 4      | «Опт» / коэф. Кл                                                       |
| **5**  | **Настоящая шапка**: `ПИН застройщика`, `Номер разрешения`, `Номер проекта`, `Этап`, `Номер помещения/Квартира…`, … |
| 6      | `ИТОГО` (SUBTOTAL по K, N, O)                                          |
| 7      | `Сумма с учетом вывода` (SUBTOTAL ради контроля)                       |
| 8…     | Данные (по одной квартире на строку)                                   |

Старый парсер брал заголовки из строки 1, где в большинстве колонок пусто, и
все ключи в `ParsedRow.Cells` оказывались `""`. Маппер читал «Номер проекта»
по алиасам, получал пустую строку и на каждую квартиру выдавал
`site_mismatch` — «для строки файла N не подходит выбранный объект», даже
когда Site/ОКС в системе действительно соответствовал данным файла.

## ✅ Правильная реализация

### 1. `Tabular(HeaderAnchors)` — подсказка парсеру

`FileLayoutHint`:

```csharp
public sealed record Tabular(IReadOnlyList<string>? HeaderAnchors = null)
    : FileLayoutHint;
```

Анкоры — это «опорные» имена колонок, которые маппер ждёт. Парсер сканирует
**первые 30 строк** `RangeUsed` и берёт за шапку **первую** строку, где
встретилось **≥2 анкоров** (case-insensitive equality по `Trim()` ячейки).

- Если анкоры **не заданы** — поведение legacy: первая строка `RangeUsed` =
  шапка, лист всегда обрабатывается.
- Если анкоры **заданы**, но в листе **не нашлись** — лист **пропускается
  целиком** (ни одной `ParsedRow`). Так фильтруются вспомогательные листы
  многолистовых файлов: «Общий график», «Итог», «План», «Кв_01.04.26» в
  «Ежевика короткая 1.xlsx» — у них структура «параметр-значение» или
  таблица KPI, а не реестр помещений. Без strict-skip они порождали
  десятки мусорных строк, проходивших случайные проверки маппера и
  переполнявших отчёт.

```csharp
// XlsxParser.ParseTabular — упрощённо
int headerLocalRow = 1;
if (anchorSet is not null)
{
    int scanLimit = Math.Min(totalRows, 30);
    for (int local = 1; local <= scanLimit; local++)
    {
        int count = range.Row(local).Cells()
            .Count(c => anchorSet.Contains(c.GetString().Trim()));
        if (count >= 2) { headerLocalRow = local; break; }
    }
}
```

### 3. Тихий пропуск сводных строк (`ИТОГО`, `Сумма…`, `План`, `Факт`)

В файлах заказчика непосредственно под шапкой попадаются строки агрегатов:
текст в первой колонке, формулы в числовых. Они не относятся ни к одному
помещению, но `isEmpty=false` → попадают в `ParsedRow`. Чтобы они не
порождали `site_mismatch`, маппер делает **тихий пропуск**, если все три
идентификационных поля пустые:

```csharp
if (string.IsNullOrWhiteSpace(permission)
    && string.IsNullOrWhiteSpace(projectNum)
    && string.IsNullOrWhiteSpace(stageNumRaw))
{
    _log.LogDebug("RoomsForm.Validate: row {Row} (sheet '{Sheet}') пропущена — нет НПС/РНС/Этапа.", ...);
    continue;  // НЕ добавляем MappedRow с ошибкой — это не данные
}
```

### ⚠️ Важно

- Анкоры сравниваются по **полному** trim'у ячейки, не по substring — иначе
  «Тип помещения» в подзаголовке зачитается как «Тип/Название/Вид» (нет).
- Порог **≥2 анкоров** — компромисс: одна случайная ячейка с подходящим
  текстом (например, в комментарии) не должна выдать себя за шапку.
- `SourceRowNumber` теперь **абсолютный** номер Excel-строки
  (`firstAbsRow + local - 1`). Для файлов, где `RangeUsed` начинается с 1
  (большинство), значение совпадает с прежним; для файлов с пустыми
  верхними строками теперь корректно отражает реальный номер.
- Хвостовые пустые заголовки обрезаются: если `RangeUsed` заходит за
  пределы значимых колонок, пустые ключи в `Cells` иначе перетирают
  друг друга.

```csharp
// НЕПРАВИЛЬНО — берём шапку из first row of RangeUsed без анкоров.
var firstRow = range.FirstRow();
foreach (var cell in firstRow.Cells())
    sheetHeaders.Add(cell.GetString().Trim());
// → в файлах с подзаголовком над шапкой все ключи "", в маппере "Номер
//   проекта" не находится, site_mismatch на КАЖДУЮ строку.
```

```csharp
// НЕПРАВИЛЬНО — выдавать site_mismatch на строку, где вообще нет
```

## 🎯 Чек-лист при изменениях

- [ ] Если меняешь алиасы шапки в маппере — синхронизируй `HeaderAnchors`
      в `LayoutHint`, иначе автодетект сломается.
- [ ] Любой новый маппер с возможно-смещённой шапкой должен пробросить
      `HeaderAnchors`, а не полагаться на «строка 1».
- [ ] Если файл содержит сводные строки прямо в табличной части — в
      маппере используется тот же шаблон «пропуск без MappedRow».
- [ ] При появлении в файле новой колонки идентификации (например, ещё
      одного варианта названия «Этап») добавь её и в алиасы маппера,
      и в анкоры — иначе анкорный поиск может промахнуться в новых
      пользовательских файлах.
